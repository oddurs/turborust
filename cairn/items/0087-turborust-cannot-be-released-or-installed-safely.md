## Problem

Measured against what established Rust CLIs ship — ripgrep, just, watchexec,
cargo-nextest, and this project's own sibling `cairn`:

- **Known vulnerabilities in the lockfile.** Checked against the RustSec
  database: five in `rustls` 0.23.44 (behind the opt-in `tls` feature), one in
  `rustls-webpki` 0.103.15, and an unsoundness in `tokio` 1.53.1, which every
  build carries. Nothing checked for them.
- **No releases.** No binaries, no checksums, no provenance. The site told
  people to `cargo install turborust`, which fails: the crate has never been
  published.
- **No declared minimum Rust**, so a user on an older toolchain got a compile
  error in a dependency rather than a clear refusal.
- **The crate would have shipped 147 files** — every tracker item, the git
  hooks, CI config — for a build that reads two directories.
- **No security policy**, for a tool that serves files, proxies requests, opens
  a control socket and replays cached outputs.

## What was done

Ported from `cairn`, adapted rather than copied:

- Lockfile: `rustls` 0.23.46, `rustls-webpki` 0.103.16, `tokio` 1.54.1. Every
  vulnerability is gone; three "unmaintained" notices for `zbus` 5's companion
  crates remain, ignored with a reason, because they arrive through
  `notify-rust`, whose latest release still uses `zbus` 5.
- `deny.toml` and a `supply-chain` CI job (`cargo deny check`). The licence
  allow-list adds three permissive licences the tree cannot avoid, each named
  with the crate that needs it.
- `rust-version = "1.89"` — the highest any dependency declares — and an `msrv`
  job that builds with exactly that.
- An include allow-list in `Cargo.toml` (147 files → 36) and a `packaging` job
  running `cargo publish --dry-run`.
- `release.yml`: on a `v*` tag, a preflight that refuses a tag disagreeing with
  `Cargo.toml`, static musl binaries for Linux, macOS (arm64 and x86_64) and
  Windows, `SHA256SUMS`, build-provenance attestations, completions and a man
  page generated by the binary, a GitHub release, and crates.io only when a
  token exists. A pull request touching the workflow or manifest runs all of it
  except publishing.
- `SECURITY.md`, and install instructions that work today.

## Acceptance criteria

- [x] No known vulnerability in the lockfile, and CI fails on a new one
- [x] Licences checked against an explicit allow-list
- [x] The declared minimum Rust is built in CI
- [x] The published crate contains what the build needs and nothing else, checked in CI
- [x] A tag produces verifiable binaries for every supported platform; a PR exercises the same path
- [x] A security policy with a private reporting route

## 2026-10-28

The advisories and licences were checked locally before CI, so the first `cargo deny` run would not be the discovery: a script over the RustSec database found the seven issues and then confirmed the bump cleared all but the three ignored notices, and a small SPDX evaluator confirmed every licence expression in the tree is satisfiable from the allow-list. Dependabot's open #19 already bumps `rustls` and `tokio` but not `rustls-webpki`, so it would have left one vulnerability; whichever of the two merges second needs its lockfile regenerated.

The MSRV floor came from the dependencies (`notify-rust` declares 1.89). Whether turborust's own code needs newer is what the `msrv` job is for; it builds with `cargo +1.89` explicitly, because `rust-toolchain.toml` pins `stable` and would otherwise override the toolchain the job installed.

Verified here: `cargo package` builds from the packaged tarball, so nothing the build needs is missing from the include list; the completions and man-page step runs and the bash completion loads; both workflows parse. Not verifiable here: the cross-target builds — especially `x86_64-apple-darwin` from an arm64 runner, which compiles `mac-notification-sys`'s Objective-C, and musl with `notify-rust` — which is what the pull-request dry run is for.

Needs the owner, not code: GitHub's private vulnerability reporting has to be switched on in the repository's security settings for the link in `SECURITY.md` to work. Publishing to crates.io needs a `CARGO_REGISTRY_TOKEN` secret, and is a decision about the name as much as the code.
